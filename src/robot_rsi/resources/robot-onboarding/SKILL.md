# Robot project onboarding

Interpret the requested outcome and deliverable before its casual label: capability, skill, tool and feature can describe the same user goal. Reuse an existing method for an ordinary task; use a direct capability for a simple query, add missing operations/methods/assets only as needed. One package may provide several types. Respect explicit interface/manifest/output requirements and clarify only an ambiguity that changes scope or results; do not ask the user to classify terms. Keep machine manifests and actual registration strict.

The same project Agent can integrate, execute and improve methods with already-authorized tools; these are work purposes, not identities. Use existing recovery or correct conditions before changing code. Work on project-owned extensions and methods. Use the host-selected fixed Harness installation, never patch installed core or base instructions for a local problem. Build/validate candidates in the writable project. Controlled coding candidate_install uses the local parent program to install compatible additions under fixed core/base constraints, then resumes this same session; no person or other Agent is needed for normal local installation. Preserve old task/install references and verify new code in sourced new tasks. Report a reproducible public gap to the maintainer. Host facts establish actual protection; a lock, note or these instructions do not.

Start from the original goal and supplied environment facts. Ordinary runtime reuses installed methods without repeating onboarding. A specific standalone data/inspection task keeps its own scope. For initial robot integration, recommend the applicable foundation: independent environment; control/state, named joints/tools and supported stop/hold/feedback; FK/IK and geometry; camera observations; required model/TCP/frame/calibration assets. Tailor it to the robot and actual source, making missing or inapplicable items explicit. Reading a state or image is foundational sampling; recording episodes/datasets, teleoperation, human-in-the-loop correction and policy inference are optional upper workflows.

Reuse an explicit user scope or still-applicable saved choice. Otherwise recommend the foundation and ask one grouped question about discovered extensions for the first version. Finish the foundation analysis/plan while awaiting a choice; leave extensions unselected rather than treating silence as consent. "All" still needs an ordered first batch and its dependencies, not a wholesale migration. Do not ask separately for every capability or repeat an answered choice. A later requested extension reuses the installed foundation and bindings, revisiting only its relevant source and dependencies.

Use `project_files` selectively on README/configuration, implementation and tests; cite paths/symbols and reuse valid notes/bindings. Do not execute the legacy application during discovery. A plan needs implementable decisions; implementation needs artifacts/calls, not a renamed "offline analysis" goal.

Read needed public guidance through `harness_read(guide="integration" or "interfaces")`, following offsets. Use `tool_describe` for chosen tool inputs and existing read-only directories for installed capabilities/resources. Framework contracts and documentation do not prove that this robot has an implementation. Deliver these four decisions together, with the key decisions in the Chinese answer:

In a usage project created by `robot-rsi init`, work in that current directory using the coding host's already-authorized file/terminal tools. `robot-rsi guide agent` exposes the installed base, this workflow and the project guide without starting a child Agent. Keep Harness as a fixed dependency; use the existing development/runtime profiles and local extensions/skills/assets/state. Do not relocate work under an external state directory or turn the project into a framework mirror. The built-in source-only client remains for read-only plans; its missing development tools do not limit a coding host that has them.

1. **Usage environment.** Name the read-only source root, host-selected usage_root, current Python/installation and what is known or unknown about the target environment. A selected path is not an installed environment or permission grant. Prefer a prepared independent Harness environment; otherwise specify the target's pyproject.toml/uv.lock/.venv, fixed core/extension sources and dependency differences. An already selected target needs no repeated confirmation; an absent target is a specific missing input. Keep configuration/assets/state outside .venv, never install in the legacy environment.

2. **Capability destinations and scope.** Cover the applicable foundation and user-selected extensions, with the scope basis (user choice or recommendation/pending choice). For each relevant source module/symbol/version, classify resource, capability, implementation, task method, asset or configuration. Choose fixed package installation, thin adaptation, selected extraction, existing service contract or versioned asset reference/needed copy; give the reason, artifact/maintenance location and owner. A unique device writer does not make an old application API mandatory. Leave old sources/environments/services unchanged unless separately authorized; no whole-project copy, legacy PYTHONPATH/editable dependency or automatic writeback. Reuse depends on actual contracts/SDKs/evidence; instance calibration stays local. Deferred extensions need only a short source entry and purpose, not a second full catalog, extracted code or installed dependencies.

3. **Concrete contract mapping.** Name the installed port/tool and contract version. Map source input/output to actual target fields, showing units, named joints/tools, frames, acquisition clocks and status semantics where relevant. Separate direct mappings, computable conversions, missing source information and unsupported public semantics. Assign every gap to a local adapter/method, missing source/device feedback, asset/configuration or a specific framework change. Optional preview metadata may stay absent with an honest qualification; do not invent precise state, timestamps or unsupported capability names. Read actual guide/schema details instead of listing only generic capability names. A plain computation/data check need not become a new generic provider; stable goal-driven methods can be code skills.

4. **First runnable task.** For robot integration, choose a step within the applicable foundation, retaining control/camera/kinematics gaps in the overall plan. Do not substitute an unrelated easy data check. Name explicit inputs, minimum package/provider/skill/assets/configuration, locations, fixed installation, actual call entry, verifiable outputs and unfinished items. Offline fixed inputs may exercise control state/command receipts, camera and available FK/IK; distinguish acceptance receipts, sampled completion, synthetic/recorded checks and field validation. Do not invent a solver or declare physical readiness. Distinguish created, installed, invoked and verified. Use existing Profile/Runtime/Registry/Store; install at task boundaries with `uv sync --locked --no-dev --no-editable`, run executables or `uv run --no-sync`, preserving active pins. System SDK/CUDA/CAN deployment remains separate.

Save brief scope basis, selected foundation/extensions, installed bindings/assets, foundation gaps and deferred source/use pointers in the existing `workspace_note` when relevant. Update the same facts when the user chooses or evidence changes; do not preload deferred business details into ordinary runtime. Keep each text within its schema (at most 2400 characters), split topics when needed, and leave long explanations for the final answer. Only after successful saves, reference actual keys in `task_finish` (`kind=workspace_note`, id=key); only after finish succeeds, call `task_archive`. Correct rejected predecessor calls before advancing. A plan may conclude with these sourced decisions and a pending extension question; pending is not user confirmation. Authorized implementation continues through artifacts, installation and necessary calls with host development tools, otherwise hand off the exact unfinished work/tool gap. Report the four decisions, scope/choice question where needed, evidence and gaps in Chinese. A plan is not successful implementation.

Useful shared candidates may leave a short source/version/interface/check record for maintainers, without blocking ordinary local work or automatically uploading/sending messages. No extra review, per-step summary or routine approval is required.

For an authorized implementation, each independently deliverable feature/fix finishes with relevant checks, updated existing fact owners/short checkpoint and an actual local Git commit. Use the coding host's terminal and installed project guide; preserve unrelated staged/unstaged work. Report SHA, tested scope and gaps. Missing Git tools/identity/access leave an explicit uncommitted handoff; a restricted worktree uses an authorized host commit without exposing shared Git metadata. Do not push, initialize a nested repository or change global identity. Respect no-commit requests; ordinary runtime has no Git step. Resume/write back through workspace_context and existing project materials, not a new memory tree.

Implementation also delivers two concise views from actual catalogs: capability/resource/implementation/contract/asset and readiness or gap; task skill/dependencies/version/call and result evidence. Use `capabilities_list`, `resources_list`, `skills_list` and `skill_describe`, not a static all-success inventory. Deliver at least one reusable daily code method (for example state plus selected camera observation with source/freshness/missing information), distinct from onboarding instructions and a one-off acceptance script. Discover and run that installed method through `task_run`; preserve real observations, operation/result references and restart reuse. Package names or future skill plans alone do not complete implementation. Connection lifecycles and operation waits share one Runtime/host; reuse a host's already-connected resources, calling the exposed `resource_connect` only when needed. Separate one-shot CLI processes do not preserve connections. Ordinary runtime tasks reuse the installed method without repeating onboarding or satisfied prerequisites.
