# Robot project onboarding

Start from the original user goal and supplied environment facts. A plan request needs decisions someone can implement; an implementation request needs actual artifacts/calls, not a renamed "offline analysis" goal. Ordinary runtime reuses installed methods without repeating onboarding. Use `project_files` selectively on relevant README/configuration, implementation and tests; cite paths/symbols and reuse valid notes/bindings. Do not execute the legacy application during discovery.

Read needed public guidance through `harness_read(guide="integration" or "interfaces")`, following offsets. Use `tool_describe` for chosen tool inputs and existing read-only directories for installed capabilities/resources. Framework contracts and documentation do not prove that this robot has an implementation. Deliver these four decisions together, with the key decisions in the Chinese answer:

1. **Usage environment.** Name the read-only source root, host-selected usage_root, current Python/installation and what is known or unknown about the target environment. A selected path is not an installed environment or permission grant. Prefer a prepared independent Harness environment; otherwise specify the target's pyproject.toml/uv.lock/.venv, fixed core/extension sources and dependency differences. An already selected target needs no repeated confirmation; an absent target is a specific missing input. Keep configuration/assets/state outside .venv, never install in the legacy environment.

2. **Capability destinations.** For each selected source module/symbol/version, classify resource, capability, implementation, task method, asset or configuration. Choose fixed package installation, thin adaptation, selected module extraction, existing service contract or versioned asset reference/needed copy, and explain why. Name the artifact/new maintenance location and execution owner. A unique device writer does not make an old application API mandatory. Leave originals/locks/.venv/configuration/services unchanged unless separately authorized; no whole-project/environment copy, legacy PYTHONPATH/editable runtime dependency or automatic writeback. Similar models only suggest candidates; reuse follows actual SDK/dependencies/contracts and evidence, while instance calibration stays local.

3. **Concrete contract mapping.** Name the installed port/tool and contract version. Map source input/output to actual target fields, showing units, named joints/tools, frames, acquisition clocks and status semantics where relevant. Separate direct mappings, computable conversions, missing source information and unsupported public semantics. Assign every gap to a local adapter/method, missing source/device feedback, asset/configuration or a specific framework change. Optional preview metadata may stay absent with an honest qualification; do not invent precise state, timestamps or unsupported capability names. Read actual guide/schema details instead of listing only generic capability names. A plain computation/data check need not become a new generic provider; stable goal-driven methods can be code skills.

4. **First runnable task.** Choose one explicit goal/input, the minimum package/provider/skill/asset/configuration artifacts, their locations, fixed installation and actual call entry, expected verifiable output/criterion and remaining implementation items. It must follow the source and contracts above, not just a list of future phases. Distinguish created, installed, invoked and verified. Use existing Profile/Runtime/Registry/Store; install at task boundaries with `uv sync --locked --no-dev --no-editable`, run executables or `uv run --no-sync`, preserving active pins. System SDK/CUDA/CAN deployment remains separate.

For a plan/inspection, save short decisions and sources in `workspace_note` within its schema (text at most 2400 characters); split factual topics into keys if needed and leave long explanations for the final answer. Only after a successful save, reference the actual saved key in `task_finish` (`kind=workspace_note`, id=key); only after a successful finish, call `task_archive`. Follow each predecessor's actual result: correct a rejected save/finish before continuing. No physical operation is needed. For authorized implementation, complete the minimum artifacts, installation and necessary calls with host development tools; otherwise hand off the exact unfinished work/tool gap. A plan is not successful implementation. Report the four decisions, evidence and gaps in Chinese, including environment choices and contract gaps.

Useful shared candidates may leave a short source/version/interface/check record for maintainers, without blocking ordinary local work or automatically uploading/sending messages. No extra review, per-step summary or routine approval is required.
